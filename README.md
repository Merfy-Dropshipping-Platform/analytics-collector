# analytics-collector

Сборщик и приёмник аналитики витрин Merfy: `/collect` принимает события от
`static/tracker.js`, пишет их в `bronze.events`, а `internal/rpc` отдаёт отчёты
через RabbitMQ RPC.

## Пометка трафика

Каждое событие в `bronze.events` помечено колонкой `traffic_type`
(`migrations/016_traffic_type.sql`, `internal/traffictype` — общие константы
для `internal/handler` и `internal/consumer`). Три значения:

- **human** — обычный посетитель. Значение по умолчанию.
- **bot** — робот: поисковики, соцсети/мессенджеры с превью ссылок, проверки
  скорости и мониторинг, ИИ-агенты, HTTP-клиенты и библиотеки (список —
  `internal/botua`), а также браузер под управлением программы
  (`navigator.webdriver === true`, ловит `static/tracker.js`).
- **internal** — свой браузер: витрина открыта с `?mfy_owner=1` в адресе.
  `static/tracker.js` держит метку тремя каналами: переменная в памяти (живёт
  ровно одну загрузку страницы — работает, даже если оба хранилища ниже
  недоступны одновременно), `localStorage` (без срока — до явной очистки) и
  cookie **на 365 дней** (единственный из трёх каналов, у которого вообще есть
  срок годности). Любого из трёх достаточно; недоступность одного канала не
  должна ронять остальные — каждое обращение к хранилищу в своём `try/catch`.
  Скрипт сразу убирает параметр из адреса через `history.replaceState`
  (сохраняя `history.state` — важно для клиентских роутеров типа Astro,
  остальные параметры и `#` тоже не трогает). `?mfy_owner=0` снимает метку.

Классификация — на сервере (`internal/handler/collect.go`), по порядку,
первое совпадение:

1. подпись браузера запроса `/collect` (User-Agent) из списка ботов
   (`internal/botua.IsBot`) или пустая → `bot`. **Исключение:** для событий
   `purchase` и `order_cancel` эта проверка пропускается — их шлёт то браузер
   (страница после оплаты), то сервер заказов (Node fetch, подпись `node` или
   вовсе пустая, ничего не говорящая о посетителе), а деньги (см. ниже)
   всё равно не фильтруются по `traffic_type` — обход им не вредит;
2. иначе поле события `traffic:"bot"` (робота увидел сам браузер,
   `navigator.webdriver`) → `bot`;
3. `traffic:"internal"` (метка владельца) → `internal`;
4. иначе → `human`.

**Что не хранится:** сама подпись браузера (User-Agent) и клиентская
подсказка `traffic` — в очередь и в логи попадает только результат
классификации (`traffic_type`), не исходные значения.

**Что должно считаться только по `human`:** посетители, визиты, просмотры,
воронка, конверсия, сессии по локациям, каналы. Выручка и заказы (`purchase`,
`order_cancel`) — по всем типам трафика без фильтра, это деньги. **Важно:**
сама фильтрация отчётов по `traffic_type` — задача другого куска (P2,
`analytics.dashboard`/`analytics.funnel`/…, `internal/rpc` и матвью в
`migrations/`); этот кусок только проставляет и пишет колонку. До выкатки P2
колонка в базе есть, но ни один отчёт её ещё не читает.

## Тесты с базой на чистой БД: нужна партиция текущего месяца

`bronze.events` — партиционированная таблица (`migrations/002_bronze_events.sql`,
`PARTITION BY RANGE (created_at)`); миграции создают партиции только на
февраль–май 2026. Партиции на остальные месяцы в проде заводит фоновый цикл
сервиса (`internal/db.EnsurePartitions`, текущий месяц + 3 вперёд) — на свежей
базе без запущенного сервиса его никто не создаёт. Вставка события с
`created_at = now()` в любой другой месяц падает с `no partition of relation
"events" found for row`. Перед `go test -tags dbtest` на чистой БД создайте
партицию текущего (и, для запаса, следующих 1–2) месяца вручную:

```bash
docker exec <контейнер_postgres> psql -U postgres -d postgres -c \
  "CREATE TABLE IF NOT EXISTS bronze.events_2026_09 PARTITION OF bronze.events \
   FOR VALUES FROM ('2026-09-01') TO ('2026-10-01');"
```

(Год/месяц и границы — под текущую дату; `traffic_type`-колонка и её
CHECK-констрейнт наследуются на партицию автоматически, отдельно создавать не
нужно.)
